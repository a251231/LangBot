# ADR 0001：问道增长域存储与一致性

- 状态：Accepted
- 日期：2026-07-20
- 修订：2026-07-22，补充按群回复开关的持久化 owner 与兼容边界
- 决策范围：`wendao_signin_plugin` 的推广、积分、商品、卡密、权益、操作日志和按群回复开关存储
- 依据：问道增长域设计规格第 8、10、12 节；问道增长域实施计划的 Architecture、Compatibility Boundary、Risks 和 Retirement

## 背景与范围

问道插件现有 `AccountStore` 负责账号凭据、签到状态和调度状态。增长域新增推广关系、积分、商品、卡密、兑换记录和使用权益；这些数据有不同生命周期，也需要在中断后恢复。插件运行在独立进程中，当前 `BinaryStorage` 只提供按键读写、删除和列出键，没有跨键数据库事务；本期目标容量是单机器人约 1 万用户和数万张卡密。

本 ADR 固定增长域的持久化 owner、事实源、跨键写入的一致性办法、单进程并发边界和外部数据库升级触发条件。`GrowthStore` 是全部增长持久化状态的唯一 owner。它不改变现有签到流程，也不在本期设计多进程共享或外部数据库迁移。

## 候选方案

### 方案一：扩展 `AccountRecord`

把推广、积分、商品或权益字段追加到现有账号记录。实现入口少，但会把签到凭据实体变成多个领域的聚合，导致账号记录频繁重写、字段生命周期耦合、卡密和流水无法自然表达，也会破坏 `AccountRecord v1` 的兼容边界。

### 方案二：单 JSON 文档

按机器人或用户保存一个包含增长域全部状态的 JSON 文档。结构直观，单文档替换可以简化少量写入；但单文档会形成热点，积分流水和卡密库存会随规模持续膨胀，任一损坏影响范围大，且无法在文档内部为每个业务步骤提供可审计的恢复点。

### 方案三：分片记录加操作日志

为增长域建立独立、版本化的键空间，按 `bot_uuid` 和身份摘要分片；积分流水、卡密状态等不可变或状态记录保存为事实源，余额和库存只作可重建快照。跨键业务先写 `PENDING` 操作日志，按步骤幂等应用，最后写 `COMMITTED`。

## 决策

采用方案三：分片记录加操作日志。

选择理由：

1. 保持 `AccountStore` 的单一职责和 `AccountRecord v1` 稳定，增长域可以独立演进。
2. 分片限制单次读写和索引重建的范围，适配单机器人约 1 万用户、数万张卡密的本期容量；卡密池、兑换记录和用户兑换索引单分片建议不超过 500 条。
3. 积分流水与卡密状态可审计、可重建，余额和库存快照损坏时可以从事实源校正。
4. `BinaryStorage` 没有跨键事务时，操作日志为多键变更提供明确的中断点、恢复入口和幂等合同。

2026-07-22 增补的群聊回复开关继续复用 `GrowthStore` 的版本化键和单进程锁。已比较 Manifest 全局配置、Listener 进程内集合和主插件策略配合持久化记录三种方案；前两种分别缺少按群动态控制和重启恢复能力。群开关是单键布尔状态，使用单键原子替换，不进入跨键操作日志。

### Owner 与事实源映射

| 数据或能力 | 唯一 owner | 事实源或约束 |
| --- | --- | --- |
| 问道账号凭据、签到状态、调度状态 | `AccountStore` | `AccountRecord v1`，键前缀 `account:v1:` 保持原样 |
| 推广、积分、商品、卡密、兑换、权益、配置、秘密和操作日志等全部增长持久化状态 | `GrowthStore` | 新增长域键空间按 `bot_uuid` 分片，身份部分使用摘要 |
| 按群回复开关 | `GrowthStore` | `group-reply:v1:` 按 `bot_uuid + group_hash` 保存；主插件是群命令策略的唯一判断 owner |
| 积分余额 | `GrowthStore` | `point-entry:v1:` 不可变积分流水是事实源；`point-account:v1:` 账户余额是带最后流水 ID 的可重建快照 |
| 卡密库存和状态 | `GrowthStore` | `card:v1:` 卡密状态 `AVAILABLE → ISSUED → ACTIVATED` 是事实源；`card-pool:v1:` 卡密池和库存数量是快照 |

积分服务、商城服务、`GrowthService` 和 `EntitlementService` 只负责业务规则与操作编排，不是并列持久化 owner，也不直接定义另一份持久化状态；它们的全部持久化读写都通过 `GrowthStore` 完成。

增长域使用以下版本化实体前缀，不使用统一的 `growth:*:v1` 总前缀：

```text
promoter:v1:
invite-code:v1:
referral:v1:
point-account:v1:
point-entry:v1:
product:v1:
card:v1:
card-pool:v1:
redemption:v1:
redemption-index:v1:
entitlement:v1:
growth-op:v1:
growth-config:v1:
group-reply:v1:
growth-secret:v1:
```

各实体前缀后均包含 `bot_uuid`，需要按用户定位的键再使用身份摘要。

### 操作日志与幂等恢复

`BinaryStorage` 单键写入只提供原子替换语义，不假设跨键事务。涉及双向奖励、兑换、激活、库存或管理员积分调整的操作使用 `growth-op:v1:<bot>:<operation_id>` 记录：

1. 在任何业务事实写入前创建状态为 `PENDING` 的日志，保存业务 payload、步骤清单和已应用步骤。
2. 在同一增长域锁内逐步写入事实源或快照；每个步骤使用稳定的 `operation_id`（以及步骤标识）做幂等检查，已经落过的步骤直接复用结果。
3. 每个步骤成功后记录 `applied_steps`。所有步骤完成后将日志改为 `COMMITTED`。
4. 如果进程在任一步骤中断，启动恢复扫描 `PENDING` 日志，从未完成步骤继续；即使事实写入已经完成但步骤标记尚未写入，幂等检查也只保留一份流水、卡密发放或权益变更。

`operation_id` 是一次业务动作的唯一键：重复事件、消息重试和恢复重放必须得到同一最终状态。外部回复发送失败不回滚已提交的积分或卡密，用户通过兑换记录取回已持久化结果。

### 单进程锁边界

每个 `bot_uuid` 维护一个独立的 `asyncio.Lock`。锁覆盖从读取余额/库存和校验前置条件，到写入事实源、快照、操作步骤和最终提交的完整临界区，至少串行化以下操作：有效拉新双向发积分、商品兑换、卡密激活、管理员库存和积分调整，以及增长域初始化恢复。

该锁只在当前插件进程内生效，不提供跨进程、跨主机或跨实例互斥；不同 `bot_uuid` 之间互不阻塞。假设同一增长分片同时只有一个插件进程写入，是本期明确的运行边界。

### 容量边界与升级触发

本期继续使用 `BinaryStorage`，并以启动恢复和键扫描基准测试观测容量。当出现任一条件时，停止扩大当前方案并启动单独的外部数据库迁移 ADR、数据迁移和回滚设计评审：

- 同一 `bot_uuid` 需要多进程或多实例共享增长状态；
- 单机器人用户数超过约 1 万；
- `PENDING` 恢复耗时超过 30 秒；
- 约 5 万个增长键的扫描或索引重建延迟已不可接受。

上述条件是升级评审触发器，不是本期外部数据库实现内容。

## 兼容性与回退

- `AccountRecord v1` 及 `account:v1:` 序列化格式保持不变，账号解绑仍只删除问道凭据。
- 增长域使用上述新增版本化实体键空间；旧版本插件不识别这些键时，新增数据保持留存，不回写旧账号记录。
- 群聊回复默认关闭；旧版本忽略 `group-reply:v1:`，重新升级后继续读取原开关状态。
- 回退到旧插件版本时，既有签到、补签、周报和调度继续读取原账号数据；重新升级后由增长域恢复任务继续处理未提交操作。
- 当前版本不做外部数据库、多进程共享、密钥轮换或跨实例迁移；这些事项需要新的架构决策。

## Retirement 与延后边界

本期没有既有增长域 owner 或增长数据需要迁移，`AccountStore`、`SigninWorkflow` 和 `SigninScheduler` 保留原职责，通过增长服务和可选回调扩展。新增增长键在旧版本运行期间保留，重新升级后继续使用。

外部数据库、多进程共享、密钥轮换和跨实例迁移由容量或部署触发条件启动后续 ADR。多级推广、多级团队和多级返佣，现金佣金、提现与支付能力，实体商品、人工履约和外部发卡平台均属于后续能力，不进入本期增长域实现。

## 后果与风险

采用本方案会增加分片索引、操作日志和恢复代码，实施与测试成本高于单 JSON 文档。锁和单进程假设简化了本期并发控制，但多实例误写同一机器人时仍存在竞态；升级触发器必须通过容量基准和运行监控持续验证。增长域密钥丢失会影响未激活卡密的读取，密钥记录应与插件存储一起备份。

## 基线同步

本 ADR 与设计规格、实施计划和已实现的群聊回复策略保持一致；`GrowthStore` 持久化 owner、主插件策略 owner、键空间、事实源、恢复流程和容量边界均已同步。当前 `docs/aegis/baseline/` 没有已发布快照，因此本次没有可更新的基线文件。后续实现若改变 owner、事实源或兼容边界，必须先更新或新增 ADR，再调整实现。
