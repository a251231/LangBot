# 问道签到助手社区增长与积分商城设计规格

## 1. 文档状态

- 状态：用户已确认设计，等待规格审阅。
- 目标版本：下一次插件功能版本。
- 适用范围：单机器人约 1 万用户、卡密库存约数万张以内。
- 实现前提：先完成本规格审阅，再进入实施计划。

## 2. 目标与范围

### 2.1 目标

为已绑定问道账号的用户提供一层推广能力，并形成以下闭环：

```text
推广码登记 → 新用户绑定 → 首次签到确认 → 双向积分 → 积分兑换卡密 → 卡密激活续期
```

### 2.2 本期范围

- 每个已绑定用户自动获得一个稳定推广码。
- 新用户在首次绑定前登记推广码。
- 首次绑定并由插件确认首次签到成功后，关系转为有效拉新。
- 推广员和受邀人分别获得可配置积分。
- 管理员创建、上下架商品并增加卡密库存。
- 商品类型限定为插件使用期限卡密。
- 用户兑换后获得可转赠卡密。
- 用户激活卡密后延长插件使用期限。
- 到期后暂停问道业务功能，保留推广、积分、商城、兑换和激活入口。

### 2.3 暂缓范围

- 多级团队和分级返佣。
- 现金佣金、提现和支付接口。
- 实体商品或需要人工履约的商品。
- 外部发卡平台。
- 独立运营后台。
- 多进程共享同一份推广和商城状态。

## 3. 已确认业务规则

### 3.1 推广员与归因

- 所有成功绑定问道账号的用户自动成为推广员。
- 现有账号在功能上线后自动获得推广码，但不进入历史受邀关系。
- 新用户先发送 `问道邀请 <邀请码>`，再执行登录或绑定。
- 第一个有效邀请码登记后锁定，后续邀请码不覆盖原关系。
- 已经绑定过账号的聊天用户进入邀请码命令时，返回当前状态，不创建新关系。
- 自邀、重复登记和同一问道账号重复归因只记录结果，不发放积分。
- 关系范围按 `bot_uuid` 隔离。

### 3.2 有效拉新

关系状态：

```text
pending → bound → effective
pending 或 bound → rejected
```

- `pending`：已登记邀请码，尚未绑定账号。
- `bound`：首次绑定成功，等待首次签到确认。
- `effective`：插件确认首次签到状态为成功。
- `rejected`：触发自邀、重复问道账号或其他归因校验失败。
- 同一关系最多进入一次 `effective`，有效拉新积分最多发放一次。
- 推广统计只展示汇总，不展示受邀人昵称、角色或用户标识。
- 登记人数统计 `pending + bound + effective`，排除 `rejected`。
- 已绑定人数统计 `bound + effective`。
- 有效人数统计 `effective`，近 7 天新增有效人数按 `effective_at` 计算。

### 3.3 积分

- 有效拉新发生时，推广员和受邀人分别获得积分。
- 推广人积分和受邀人积分是两个独立配置项。
- 积分采用不可变流水，余额是可重建的快照。
- 流水类型：`referral_reward_promoter`、`referral_reward_invitee`、`redeem_debit`、`admin_adjustment`。
- 普通兑换保持余额非负。
- 每个奖励或扣除动作携带唯一 `operation_id`，重复事件只产生一笔流水。

### 3.4 商品、库存与卡密

商品字段：

- `product_id`
- `name`
- `points_cost`
- `extension_days`
- `enabled`
- `created_at`

库存以卡密记录为事实源，卡密状态为：

```text
AVAILABLE → ISSUED → ACTIVATED
```

- 管理员增加库存时由插件生成高强度随机卡密。
- 卡密原文使用当前机器人的增长域密钥加密保存，同时保存哈希索引。
- 首次初始化增长域时生成 32 字节随机密钥并保存为独立秘密记录，后续重启复用该密钥。
- 密钥轮换和跨实例迁移属于后续运维能力；当前版本保留原密钥即可读取历史卡密。
- 用户兑换商品时扣积分、消耗一张 `AVAILABLE` 卡密并返回卡密原文。
- 卡密可转赠，兑换人和激活人可以是不同用户。
- `问道兑换记录` 允许兑换人再次查看自己已发放但尚未激活的卡密。
- 同一张卡密首次激活成功后永久进入 `ACTIVATED`。
- 商品下架只影响后续兑换，已经发放的卡密保持可激活。
- 卡密记录保存生成时的商品名称和延长天数快照，后续商品变化不改变历史卡密权益。

### 3.5 使用期限

- 现有账号的初始期限从首次启用增长功能时的持久化 `rollout_at` 开始计算。
- 新账号的初始期限从首次绑定成功时间开始计算。
- 初始试用天数由管理员配置，默认值建议为 30 天。
- 首次启用增长域且 `rollout_at` 尚未存在时，插件在增长域锁内保存 `rollout_at`，扫描已有账号并幂等创建初始权益和推广员记录。
- 初始化中断时由操作日志继续处理尚未初始化的账号，已经初始化的账号保持原到期时间。
- 卡密激活使用以下公式：

```text
new_expiry = max(now, current_expiry) + extension_days
```

- 到期后暂停查询、签到、补签、周报和自动调度。
- 到期后保留推广、积分、商城、兑换、激活和权益查询。
- `问道解绑` 只删除问道账号凭据，推广关系、积分、卡密记录和权益状态继续保留。
- 重新绑定账号时沿用原聊天用户的增长状态，不重复发放试用期。

## 4. 用户命令

```text
问道推广
问道邀请 <邀请码>
问道积分
问道商城
问道兑换 <商品ID>
问道兑换记录
问道激活 <卡密>
问道权益
```

`问道推广` 返回：推广码、登记人数、已绑定人数、有效人数、近 7 天新增有效人数。

`问道商城` 返回：商品 ID、名称、积分价格、延长天数和当前可用库存。

`问道兑换` 成功回复卡密原文；卡密、Token、手机号和其他敏感字段不进入日志、设置页或推广统计。

## 5. 管理员命令与配置

管理员通过 manifest 配置 `admin_user_ids`，使用逗号分隔的聊天用户 ID。管理命令只在机器人私聊中执行。

建议命令：

```text
问道管理 商品新增 <名称> <积分> <天数>
问道管理 商品上架 <商品ID>
问道管理 商品下架 <商品ID>
问道管理 库存增加 <商品ID> <数量>
问道管理 商品列表
问道管理 积分规则 <推广人积分> <受邀人积分>
问道管理 积分调整 <用户ID> <数量> <原因>
问道管理 统计
```

建议 manifest 配置：

```text
admin_user_ids
growth_trial_days = 30
promoter_reward_points = 100
invitee_reward_points = 20
```

管理员调整商品、库存、积分规则和积分余额都产生审计流水。

- manifest 值用于首次创建当前机器人的增长配置。
- `问道管理 积分规则` 保存运行时配置，只影响之后转为有效的推广关系。
- 试用天数调整只影响之后首次绑定的账号，已有权益到期时间保持原值。
- 已生成卡密的延长天数采用卡密快照，商品后续变化保持历史卡密原值。
- 商品名称长度为 1 至 50 个字符。
- 商品积分价格范围为 1 至 1,000,000。
- 单张卡密延长天数范围为 1 至 3,650 天。
- 单次增加库存范围为 1 至 1,000 张。
- 单项推广奖励范围为 0 至 1,000,000 积分。
- 管理员积分调整后余额保持非负，调整原因长度为 1 至 200 个字符。

## 6. 模块与数据 owner

### 6.1 保留的既有 owner

- `AccountStore`：问道账号凭据、签到状态、调度状态。
- `SigninWorkflow`：签到和首次签到确认。
- `SigninScheduler`：自动任务调度。
- `command_parser.py`：命令词法解析。
- `WendaoSigninListener`：事件过滤、私聊限制和消息回复。

### 6.2 新增 owner

- `GrowthStore`：推广、积分、商品、卡密、权益和操作日志存储。
- `GrowthService`：用户命令、管理员命令和业务编排。
- `EntitlementService`：权益初始化、到期判断和卡密激活。

禁止把商城、积分和权益字段追加到 `AccountRecord`，避免签到凭据实体承担多个领域职责。

### 6.3 既有流程集成

- `_verify_and_save_binding` 保存账号后调用 `GrowthService.on_account_bound`，推进推广关系并初始化新用户权益。
- `SigninWorkflow` 接收可选的 `on_signin_confirmed` 回调；最终状态确认 `signInStatus == 2` 后调用增长域。
- 增长域回调失败时，签到结果仍正常返回，积分操作保持为 `PENDING` 并由启动恢复继续处理。
- `SigninScheduler` 在判断账号任务到期前查询 `EntitlementService`，过期账号跳过每日任务和自动周报。
- 手动问道业务命令在进入 `SigninWorkflow` 或 `WeeklyReportService` 前执行同一权益检查。
- 推广、积分、商城、兑换、激活、权益和管理员命令绕过业务权益检查。

## 7. 持久化键与索引

所有键按 `bot_uuid` 分片，身份部分使用摘要，避免直接把用户 ID 放入存储键。

```text
promoter:v1:<bot>:<identity_hash>
invite-code:v1:<bot>:<code>
referral:v1:<bot>:<invitee_hash>
point-account:v1:<bot>:<identity_hash>
point-entry:v1:<bot>:<entry_id>
product:v1:<bot>:<product_id>
card:v1:<bot>:<card_hash>
card-pool:v1:<bot>:<product_id>:<shard_id>
redemption:v1:<bot>:<redemption_id>
redemption-index:v1:<bot>:<identity_hash>:<shard_id>
entitlement:v1:<bot>:<identity_hash>
growth-op:v1:<bot>:<operation_id>
growth-config:v1:<bot>
growth-secret:v1:<bot>
```

余额和商品库存可以保存快照用于查询性能，但积分流水和卡密状态是最终事实源。

- 卡密池、兑换记录和用户兑换索引按固定容量分片，单个分片建议最多 500 条记录。
- 余额快照携带最后应用的流水 ID；发现差异时按积分流水重建。
- 库存快照携带卡密池版本；发现差异时按 `AVAILABLE` 卡密记录重建。

## 8. 一致性与恢复

同一 `bot_uuid` 使用增长域锁串行处理以下操作：

- 有效拉新双向发积分。
- 商品兑换扣积分并发放卡密。
- 卡密激活并延长权益。
- 管理员库存和积分调整。

操作日志结构：

```text
PENDING → 应用幂等变更 → COMMITTED
```

插件初始化时扫描 `PENDING` 操作并执行恢复。每个步骤以 `operation_id` 去重，重复恢复得到同一最终状态。

- 绑定成功后的增长域写入失败时，账号绑定保持成功，恢复任务继续推进 `bound` 状态。
- 有效拉新奖励失败时，签到保持成功，恢复任务继续完成双向积分。
- 兑换回复发送失败时，积分和卡密发放保持已提交，用户通过 `问道兑换记录` 取回卡密。
- 权益存储读取异常时暂停本次问道业务操作并返回通用重试提示，避免绕过到期控制。

## 9. 安全与风控

- 邀请关系、积分奖励、兑换和激活全部使用一次性幂等键。
- 同一聊天用户只能拥有一条有效邀请关系。
- 同一问道 `user_identifier` 在当前机器人范围内只计入一次有效拉新。
- 卡密原文只在兑换记录和激活输入链路中出现，日志和错误消息执行脱敏。
- 管理员命令校验用户 ID、私聊上下文和参数范围。
- 商品价格、延长天数、库存数量和积分调整数量执行上下限校验。
- 卡密激活失败不消耗卡密；激活成功后不允许再次使用。

## 10. 兼容性

- 既有问道命令保持原语义。
- 既有 `AccountRecord` 存储 schema 保持 v1，增长数据采用新增键空间。
- 当前已绑定账号通过 `rollout_at` 获得初始试用期。
- 回退到旧插件版本时，新增增长键空间保持留存，旧版本继续读取 `AccountRecord` v1。
- 多进程共享同一增长状态和超过约 1 万用户属于后续架构升级边界。

## 11. 验收标准

- 新绑定用户成功登记推广码后生成 `pending` 关系。
- 绑定成功后进入 `bound`，首次签到确认后进入 `effective`。
- 有效拉新重复触发时，推广员和受邀人各自只获得一次积分。
- 自邀、重复问道账号和已绑定用户均保持积分不变。
- 商品创建、上下架、库存增加和列表查询均受管理员权限保护。
- 积分不足、库存耗尽和商品下架时兑换状态保持不变。
- 兑换成功返回一次性卡密，兑换记录可再次查看。
- 卡密跨用户激活成功一次，第二次激活保持原状态。
- 卡密激活在过期账号上仍可用，并正确延长期限。
- 到期账号的问道业务命令和调度暂停，推广及商城命令保持可用。
- 模拟进程中断后，`PENDING` 操作恢复且不重复扣分或发卡。
- 插件重启后推广关系、积分、商品、卡密和权益全部恢复。

## 12. 架构决策信号

本设计新增增长域 owner、权益边界、操作日志和卡密兼容路径，属于持久化架构变化。实施前应记录一份 ADR，明确 `GrowthStore` 的事实源、单进程锁边界和后续外部数据库升级触发条件。
